## The problem

A tool that required expertise to use safely

The CUI tool — used to create and manage campaigns and benefits across global markets — had grown by accretion. Feature by feature, edge case by edge case, until the original logic that held it together had disappeared. By the time I came to this project, using it correctly required significant institutional knowledge. New users made errors they didn't catch. Veterans had spreadsheets and workarounds that lived outside the system.

The surface-level problem was UX friction. The deeper problem was that the logic of how campaigns and benefits related to each other wasn't visible in how the tool was structured.

## Approach

Build the case first, then the direction

Before any redesign conversation could start, the problem needed to be quantifiable. I developed a design business case — mapping stakeholder interviews, key user journeys, and cost impact factors into a clear executive summary. That gave the project the strategic weight to move forward.

The audit that followed wasn't about cataloguing UI issues. It was about understanding what mental model the tool was asking users to carry — then identifying where that model broke down. I mapped the objects (campaigns, benefits, rules, conditions), the relationships between them, and the failure points.

From that, I designed a vision for how the tool should work: one where the logic is visible, the relationships are explicit, and reusability is built in rather than hacked around.

## What I found and what I did

The core issue was that "campaign" and "benefit" had become overloaded concepts. They meant different things in different contexts, and the tool didn't help users understand which context they were in. Creating a proposal for a Benefit Management UX overhaul was one output; the more important output was a shared definition of what these objects were and how they should behave.

I mapped user intent, objects, and campaign phases into a coherent structure. From that structure, we designed a vision for how the tool should work — one where the logic was visible, the relationships were explicit, and reusability was built in rather than hacked around.

## What this kind of work actually is

This project is a good example of something I find genuinely interesting: the moment when a UX problem reveals itself to be a systems problem, and the design work shifts from "how should this look?" to "how should this work?"

The vision work here was speculative in the sense that it pointed toward a future state rather than shipping a redesign immediately. But that's appropriate for this kind of complexity — you need a clear picture of where you're going before you start making incremental changes, otherwise every incremental change just adds to the confusion.

The tangible results were about confidence and scale: users with a clearer mental model make fewer errors, escalate less, and can do more without support. The strategic win was a design direction that gave the product team something to build toward.

## A process you can follow

One of the quieter problems in the original tool was that users didn't know what creating a campaign actually involved. Experienced users had the steps in their heads. New users didn't — and the tool didn't tell them.

The creation flow now makes that process explicit in the sidebar: Create details, Set Schedule, Define rules, Review QA, Generate voucher codes, Validate, Review and launch. Each step is navigable. Users know where they are and what comes next. The QA step is built into the flow — not something that happens separately, in a spreadsheet, after the fact.

## Logic you can read

The rule builder was the part of this redesign I found most interesting to work through.

The original tool had rules — they were just invisible to the person creating campaigns. You'd configure a multi-level discount and trust that the system would apply it correctly. If it didn't, you'd find out at voucher generation or, worse, when a customer complained.

We redesigned this so the logic is explicit and readable. A benefit definition is a set of composable conditions and effects. You define when a rule applies — subscription type, customer attachment limits, product family — and then you define what it does: if redemption count equals 1, apply 50%; if it equals 2, apply 40%; and so on. The system shows its own logic rather than hiding it.

## The details that catch errors

Two specific problems kept surfacing in the audit. The first was SKU-level discount logic — users couldn't easily see what discount applied to which box size, so validation happened in spreadsheets outside the tool. A dedicated SKU-based benefit definition view solves this: a pricing grid at the level that actually matters for voucher generation, downloadable as CSV.

<ScreenRow title="SKU-level discount visibility" description="The audit found users validating SKU-level pricing in external spreadsheets. A dedicated view shows the pricing grid at the level that matters for voucher generation, exportable as CSV." />

<FullImage src="/Work/CUI/SKU%20based%20Benefit%20Definition.jpg" alt="SKU based Benefit Definition — pricing grid by box size and SKU" caption="SKU based Benefit Definition — discount logic made visible at the SKU and box size level. The second problem was what happened when something went wrong. The original tool had error states; it didn't have resolution. The activity panel separates warnings from errors, timestamps them by market, and links directly to the affected campaign. Not a generic alert — a path to the fix.

## The overview

<ScreenRow title="Campaign overview & detail" description="The overview surfaces what matters during an active campaign: vouchers attached, redemption rate, conversion, performance trend. The detail page brings campaign performance, benefit definitions, demographics, and material previews into one place." />

The campaigns overview and detail page changed too — more in emphasis than in structure. The overview surfaces the metrics that matter during an active campaign: vouchers attached, redemption rate, conversion, whether performance is trending above or below the norm. The detail page brings campaign performance, benefit definitions, customer demographics, and a preview of campaign materials into one place.

The bet was that if users could see clearly — at the list level and the detail level — what was running, what was working, and what needed attention, they'd spend less time cross-referencing tools and more time acting on what they found. Fewer manual workarounds. Fewer errors that propagate quietly until they cost money.
